## 1. Context

Phases 1–3 landed a deterministic pipeline: receive → dedup → single-shot LLM classification via `generateObject` → matrix priority → persist → emit `triaged` / `failed`. The classifier sees only the raw subject + description and produces a fixed-shape `TriageClassification`. The model gets one shot, no context, no investigation. With Gemini 3 Flash's stronger tool-use surface, we can let the classifier *investigate* — checking similar past tickets and the submitter's recent history — before committing the same structured output.

Phase 3.5 converts the **classification step only** into a bounded tool-loop, while everything else (dedup, priority matrix, persistence, retry dispatcher, event taxonomy) stays strictly deterministic. The Provider stays schema-agnostic (per the earlier Provider-can't-import-Features rule); the Feature owns the schema, the tool factory, and the request context.

Intended outcomes:

1. Better classifications on ambiguous tickets that benefit from neighborhood context (recurring incidents, user-pattern bugs).
2. No regression in determinism for the rest of the pipeline — priority is still matrix-computed; dedup is still pre-classify; the schema is unbypassable.
3. A reusable tool seam: Phase 4 can add `getActiveLinearIssues` without restructuring; future phases can grow the read-only surface incrementally.
4. Safe degraded mode: on tool-loop timeout / hard error, the Provider falls back once to the existing single-shot path so the ticket always lands `triaged` or `failed`.

## 2. Locked Decisions for This Plan

1. **Model upgrade.** `DEFAULT_MODEL_ID` in `services/providers/ai/client.ts` bumps from `gemini-2.5-flash-lite` to the verified Gemini 3 Flash model identifier, currently `gemini-3-flash-preview` in Google's model docs. Existing `AI_MODEL` env override still wins. The first implementation step re-verifies the identifier accepted by `@ai-sdk/google` 3.0.21 before merging.
2. **Tool-augmented classification only at the triage step.** Dedup, priority matrix, persistence, Linear push (Phase 4), and email (Phase 6) remain pure deterministic code. The agent has no write tools.
3. **Two tools ship in Phase 3.5.** `findSimilarTicketsForContext` and `getRecentUserTickets`. Both read-only, both org-bound via tool-wrapper closure (the agent never passes `orgId` / `userId` as tool args).
4. **Conservative guardrails.** Max 4 tool-call rounds via `stopWhen: stepCountIs(4)`; total wall-clock budget 15s via the SDK timeout / abort signal; every tool call audit-logged in `ticket_events.triaged.payload.tool_calls` as `{ name, input, durationMs, ok }`. Outputs are **not** stored (payload bloat).
5. **Single-shot fallback on budget exceed.** On tool-loop timeout OR hard error, retry once via the existing `generateObject` path (no tools). On success: persist + emit `triaged` with `payload.fallback = 'single_shot'`. On second failure: existing `persistFailure(...)` path.
6. **AI SDK surface.** Use `generateText` with `tools: { ... }` + `output: Output.object({ schema })` + `stopWhen: stepCountIs(N)` in a single call. Final structured object via `result.output`; tool-call trace via `result.steps`. Reference: `node_modules/ai/dist/index.d.ts` (`generateText` ~line 1088, `Output.object` ~line 2628, `stepCountIs` ~line 953).
7. **Provider gains a new method, doesn't replace the old one.** New `classifyTicketWithTools<T>(...)` lives alongside `classifyTicket<T>(...)`. Both stay schema-agnostic (no imports from `services/features/`). The Feature calls the tool-augmented method first and falls back to the single-shot method on timeout / hard error.
8. **Deferred tools.** `lookupTicketByExactSubject` — currently subsumed by `findSimilarTicketsForContext`; revisit post-MVP. `getActiveLinearIssues` — folded into Phase 4 alongside the Linear Provider.
9. **Three-PR delivery split** (see Section 4) so the Provider additions and the call-site flip review cleanly.

### Stage P3.5.3 — Tool factories + config constants

Goal: `buildTriageTools` and the loop constants ship; `triageTicket.ts` is not yet changed.

- [ ] Create `services/features/triage/config.ts` exporting `MAX_TOOL_ROUNDS = 4`, `TOOL_LOOP_DEADLINE_MS = 15000`, and `CONTEXT_SIMILARITY_THRESHOLD = 0.7`. Single source of truth alongside the existing `confidence.ts` constants.
- [ ] Create `services/features/triage/tools.ts`:
  - `type TriageToolContext = { orgId: string; userId: string; subject: string; description: string }`.
  - `buildTriageTools(ctx: TriageToolContext): ToolSet` returns an object with two tools. Internally maintains a `let embedPromise: Promise<number[]> | null = null;` closure so a second `findSimilarTicketsForContext` call within the same loop reuses the first embedding.
  - `findSimilarTicketsForContext`:
    - `inputSchema: z.object({ limit: z.number().int().min(1).max(20).optional() })` — note no `orgId` / `userId` / `subject` / `description` fields.
    - `description`: short factual sentence the model will read.
    - `execute({ limit })`:
      1. Resolve memoized embedding via `ai.generateEmbedding(\`${ctx.subject}\n${ctx.description}\`)`.
      2. Read the org's dedup settings and derive `windowDays = settings?.dedup_window_days ?? DEFAULT_DEDUP_WINDOW_DAYS`, preserving the same time-window policy as deterministic dedup.
      3. `const hits = await sources.dedupSignatures.findSimilarTickets({ orgId: ctx.orgId, queryEmbedding, windowDays, similarityThreshold: CONTEXT_SIMILARITY_THRESHOLD, limit: limit ?? 5 })`.
      4. Hydrate hits via `Promise.all(hits.map(h => sources.tickets.getById({ orgId: ctx.orgId, ticketId: h.ticketId })))`, drop nulls.
      5. Return `Array<{ ticketId, similarity, type, severity, status, subjectPreview }>` where `subjectPreview = ticket.subject.slice(0, 120)`.
  - `getRecentUserTickets`:
    - `inputSchema: z.object({ limit: z.number().int().min(1).max(20).optional() })`.
    - `execute({ limit })`:
      1. `const rows = await sources.tickets.listByUser({ orgId: ctx.orgId, userId: ctx.userId, limit: limit ?? 5 })`.
      2. Return `Array<{ ticketId, createdAt, type, severity, status, subjectPreview }>`.
- [ ] New `tests/unit/triageTools.test.ts`:
  - `findSimilarTicketsForContext.execute({})` uses `ctx.orgId` from the closure; hits are hydrated and null-filtered.
  - A second call within the same `buildTriageTools(ctx)` invocation does not re-embed (assert `ai.generateEmbedding` called exactly once).
  - `getRecentUserTickets.execute({ limit: 3 })` forwards `ctx.userId` and `ctx.orgId` from the closure; the tool input schema doesn't even accept those identifiers, so cross-org injection is impossible by construction (`inputSchema.safeParse({ orgId: 'something' })` includes no `orgId` in the parsed output).

### Stage P3.5.4 — Wire `triageTicket.ts` to tool-loop with fallback

Goal: classification step runs the tool loop in the happy path and falls back cleanly. `triaged` event payload carries the tool-call trace.

- [ ] Modify `services/features/triage/triageTicket.ts`:
  - After the existing `sources.tickets.getById` fetch, build tools:
    ```ts
    const tools = buildTriageTools({
      orgId: ticket.org_id,
      userId: ticket.user_id,
      subject: ticket.subject,
      description: ticket.description,
    });
    ```
  - First attempt with SDK-enforced timeout:
    ```ts
    type LoopResult =
      | { kind: 'ok'; value: Awaited<ReturnType<typeof ai.classifyTicketWithTools>> }
      | { kind: 'fallback'; error: unknown };

    const outcome: LoopResult = await ai
      .classifyTicketWithTools({
        subject,
        description,
        schema: TriageClassificationSchema,
        tools,
        maxSteps: MAX_TOOL_ROUNDS,
        timeoutMs: TOOL_LOOP_DEADLINE_MS,
      })
      .then((value) => ({ kind: 'ok' as const, value }))
      .catch((error) => ({ kind: 'fallback' as const, error }));
    ```
  - On `'ok'`: `TriageClassificationSchema.safeParse(outcome.value.result)` (defense-in-depth). On success: persist via existing `tickets.updateTriage`, emit `triaged` with `payload.tool_calls = summarizeSteps(outcome.value.steps)` and `payload.needs_human_triage = isLowConfidence(classification.confidence)`. On Zod failure: drop to fallback (treat as classifier malformed output).
  - On `'fallback'` OR defense-in-depth Zod failure: invoke existing `ai.classifyTicket({ subject, description, schema: TriageClassificationSchema })`. On success: persist + emit `triaged` with `payload.tool_calls = []` and `payload.fallback = 'single_shot'`. On second failure: existing `persistFailure(...)` with the second error's message.
- [ ] Add `summarizeSteps(steps)` helper (in `triageTicket.ts` or `tools.ts`): maps each `StepResult` → `{ name: string; input: unknown; durationMs: number; ok: boolean }`. Walk `step.toolCalls` and `step.toolResults`; pair by `toolCallId`. Final-step assistant text and tool outputs are intentionally **not** serialized.
- [ ] Update `tests/unit/triageTicket.test.ts`:
  - Mock `@/services/features/triage/tools` → `buildTriageTools` returns a stub `ToolSet`. Mock `ai.classifyTicketWithTools` for tool-loop scenarios and `ai.classifyTicket` for fallback scenarios.
  - Cases:
    - Zero-tool happy path: `classifyTicketWithTools` resolves with `steps: []`. Assert `payload.tool_calls === []`, no `payload.fallback`.
    - One-tool happy path: `steps` includes one `{ toolCallId, toolName: 'findSimilarTicketsForContext', input, … }`. Assert `payload.tool_calls.length === 1` and the input is recorded.

    - Tool-loop hard error: `classifyTicketWithTools` rejects with `new Error('boom')`; assert fallback path runs.
    - Tool-loop + fallback both fail: assert `persistFailure(...)` runs with the fallback error's message.
    - Defense-in-depth Zod reject on tool-loop result: classifier returns an object that fails `safeParse`; assert fallback path runs.

## 7. Risks and Mitigations

| Risk | Impact | Mitigation |
| --- | --- | --- |
| Gemini 3 Flash identifier mismatch — `@ai-sdk/google` 3.0.21 may use a different canonical string | Medium | First implementation step verifies the exact ID against `@ai-sdk/google` behavior; `AI_MODEL` env override absorbs whatever Google ships. Document the verified identifier in `.env.local.example`. |
| Tool-loop latency exceeds 15s under load and every ticket falls back, paying double LLM cost | Medium | Conservative `MAX_TOOL_ROUNDS = 4` keeps median well under budget. If fallback rate exceeds ~10% in production, tighten the round budget before raising the deadline. |
| Agent ignores tools and just emits the schema (zero rounds) — no value gained over single-shot | Low | Acceptable degraded mode (matches today's behavior). Track tool-use rate via `payload.tool_calls.length` on a representative ticket sample; if zero, revisit prompt and tool descriptions. |
| Tool wrapper bug leaks `orgId` from agent args instead of context | High | Tool `inputSchema` does not include `orgId` / `userId` — they cannot appear in agent args by construction. Tool tests assert this exhaustively. |
| Embedding generation per ticket inflates Provider cost | Low | Memoized within a single `buildTriageTools` invocation. If `findSimilarTicketsForContext` is never called, no embedding is generated. Phase 3 dedup also embeds; cross-feature embedding cache is a future optimization. |
| Audit log bloat in `ticket_events.payload` | Low | Tool input recorded; output is **not** (only `{ name, input, durationMs, ok }`). Bounded by `MAX_TOOL_ROUNDS = 4`. |
| Coverage drops due to new SDK-adapter function hard to unit-test | Low | `aiProvider.test.ts` already establishes the mock-`generateText`/`generateObject` pattern; same approach extends to `classifyTicketWithTools`. |
| Tool `execute` throws (e.g., Supabase outage) — agent may behave unpredictably | Medium | The SDK surfaces tool errors to the model; if the model can't recover within the round budget, the wall-clock timeout triggers fallback. Fallback uses single-shot which doesn't depend on Provider reads. Worst case: failure-state persist runs, retry endpoint resumes. |
| Defense-in-depth Zod re-parse rejects a structurally valid `output` due to subtle SDK serialization | Low | `output` is the SDK's own schema-enforced object; a Zod re-parse on it should pass except in pathological cases. On reject, fallback path runs — strictly safer than persisting an unvalidated row. |
| Operator confusion between "vector dedup" (Phase 3) and "similar-ticket tool" (Phase 3.5) — both read embeddings | Low | Document explicitly in the architecture's Triage Tool Surface subsection: dedup writes / hard-links / soft-flags; the tool is read-only and committed nothing. Different thresholds, different consumers, same underlying RPC. |
